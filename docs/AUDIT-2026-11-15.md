# FINN improvement audit — 15 November 2026

Status: findings and proposed work only. The application and deployment were not changed during this audit.

Reviewed baseline: commit `7d97e5eaed3ec3f4388f1a281ffb2cac4e176447`. Reviewed the original three-page build brief, three-page reference, implementation, saved data, recorded model evaluation, verification records and the existing mobile screenshot. Re-ran deterministic tests and type checking, ran focused lint, and exercised adversarial inputs against the existing validator. No paid model requests or new live ingestion were needed.

## Assessment

FINN has a working foundation: an 18-company inbox, real source collectors, adjustable persisted alerts, arbitrary NSE company discovery, evidence search, a functioning Hyde integration, inspectable citations, and a carefully prepared Infosys example. The next investment should make that foundation consistently trustworthy and useful across companies.

The main weaknesses are source metadata, interpretation checks, uneven analytical depth, unattended refresh and mobile information density. Adding many more research sections before these are resolved would multiply the same weaknesses.

The assignment explicitly presents the research sections and enriched event types as examples, not a mandatory checklist. It values a focused working workflow. The proposed additions below are product choices, not claims that every example must be implemented.

## Findings requiring correction

### 1. Document dates and identities need stronger verification — critical

**Confirmed defect:** snapshot document `doc-1df757408cae23c226f5` is titled “Earnings-call transcript · Jul 2026” with period “Jul 2026”. The [original TCS transcript](https://www.tcs.com/content/dam/tcs/investor-relations/financial-statements/2025-26/q1/Management%20Commentary/Transcript%20of%20the%20Q1%202025-26%20Earnings%20Conference%20Call%20held%20at%201900%20hrs%20IST%20on%20Jul%2010,%202025.pdf) says the call occurred on 10 July 2025, covered the quarter ended 30 June 2025, and was enclosed in a letter dated 14 July 2025. The original was opened during this audit.

Discovery copies a listing row's period into each linked transcript (`lib/collectors.ts:59–60`). Parsing checks company identity but does not reconcile the period against the PDF (`lib/collectors.ts:72–77`). The model validator permits years taken from a source title as supporting numeric tokens (`lib/model.ts:49–51`), so an incorrect title can also affect accepted answer attribution.

**Coverage limitation:** 25 of 35 saved document records have no verified publication date. The retrieval-time fallback conservatively excludes them from earlier historical searches; it avoids pretending they were available earlier, but leaves those searches incomplete. An older copyright footer alone is not sufficient evidence of another date error; the confirmed mismatch above is the finding.

**Proposed correction:** distinguish call date, reporting period, filing/publication date and fetch time; extract candidate metadata from primary documents; reconcile with exchange records; flag disagreements before research use. Preserve unresolved dates as unknown. Apply corrections to document records, passages and answer caches together.

**Complete when:** prepared source metadata has been reconciled; the TCS mismatch is a regression case; conflicting labels cannot silently supply the answer year; historical inclusion tests cover actual publication availability.

### 2. Valid quotations can still support incorrect answers — critical

`validateAnswer` verifies source IDs, exact text, numeric tokens and selected units (`lib/model.ts:36–68`). It does not establish speaker, direction, metric-to-value association or expectation versus actual.

Four synthetic, deliberately incorrect claims were passed to the existing validator during this audit. All four were accepted:

| Source states | Incorrect claim accepted |
| --- | --- |
| Revenue 100 crore; PAT 20 crore | Revenue 20 crore; PAT 100 crore |
| Revenue declined 5% | Revenue grew 5% |
| Management expects 5% growth | Management delivered 5% growth |
| An analyst asks about a 5% margin; management gives no guidance | Management guided a 5% margin |

These are validator probes, not evidence that the provider generated all four errors. There is also a concrete issue in the saved live evaluation: `docs/model-evaluation.json:327` attributes AI revenue figures to management, while its supporting excerpt is phrased as a question addressed to “Krithi”. The chunk omits the speaker label. The attribution cannot be established from the supplied excerpt.

**Proposed correction:** preserve speaker turns and section context; distinguish question premises from management statements; represent important financial claims as typed facts with metric, period, scope, unit and status; add claim-support review and abstention for ambiguous evidence. Keep code-owned calculations. A second model may help assess support but should not be described as a guarantee.

**Complete when:** the four probes are rejected or withheld, analyst questions are not promoted to management guidance, and reviewed real-company cases cover wrong periods, conflicting evidence, negative growth, unit changes and absent guidance.

### 3. Evaluation currently checks execution more than answer quality — high

The six-case evaluation records an `expected` description but never asserts that the answer satisfies it. Its exit condition checks HTTP status, provider errors, date eligibility and cache reuse (`scripts/evaluate-model.mjs:3–26`). It can therefore succeed on a materially incomplete or wrongly attributed answer. Three saved cases still contain rejected claims after repair; rejection is useful protection, but an answered status does not measure completeness.

**Proposed correction:** create a reviewed evaluation set spanning the prepared companies and unfamiliar tickers. Score retrieval of the required evidence, speaker/period/basis accuracy, unsupported claims, abstention, completeness, latency and token usage separately. Include plausible unsupported questions rather than relying on an obviously fictional Mars example. Use deterministic assertions where possible and recorded human review for interpretation.

**Complete when:** a known wrong answer causes evaluation failure, the critical cases have explicit expected facts and supporting passages, and results distinguish transport success from research quality. Change retrieval or models only against this baseline.

### 4. Portfolio and read-state edge cases can break normal use — high

**Confirmed by code reproduction:** `app/page.tsx:47` calculates a snapshot end using `Math.max` on the selected portfolio's snapshot events. An empty array produces an invalid date; rendering it with `toISOString()` throws `RangeError: Invalid time value`. The portfolio API allows an empty list. A portfolio containing only companies absent from the saved snapshot has the same condition. This was reproduced using the exact date calculation, not a fresh browser session.

**Confirmed request-size mismatch:** opening a filing sends the entire accumulated read list (`app/page.tsx:45`). The route allows 2,000 IDs but caps the request at 8,000 bytes (`app/api/[...path]/route.ts:28–36`). A list of 501 ordinary nine-digit NSE IDs serializes to 8,025 bytes and is rejected. Overlapping read requests can also overwrite one another because each replaces the list.

**Proposed correction:** give empty and new portfolios valid date defaults and useful onboarding; store read changes atomically as individual operations; test rapid interaction and failed requests.

**Complete when:** empty/new-company portfolios render normally, hundreds of read items remain usable, and parallel read actions preserve both changes.

## Product depth and reliability gaps

### 5. The strongest analysis is still a single historical example — high value

The verified ledger and financial results table come from one prepared Infosys FY25 record in `data/analysis.json`. `app/page.tsx:74` explicitly limits that ledger to INFY. Generic research discovery works, but it does not create equivalent comparisons. Other prepared companies mostly demonstrate search and synthesis.

The Infosys timeline correctly follows four revisions of one annual target; it is not four independent quarterly target-versus-actual comparisons. Its results table is historical Q4 FY25, with EBITDA honestly unavailable. A newly filed result does not automatically receive the same treatment.

**Proposed next depth:** build one reusable financial fact and guidance comparison path, then prove it on two contrasting additional companies. Preserve quarterly versus annual periods and explicit numeric guidance versus qualitative commentary. A company that does not guide should be shown as such. Produce results cards from the actual results attachment, with Revenue, EBITDA if supportable, PBT, PAT and like-for-like QoQ/YoY changes.

**Complete when:** at least three prepared companies demonstrate useful, independently checked analysis; an unfamiliar ticker follows the same pipeline or returns precise coverage gaps; a newly indexed results filing can open a sourced first-cut table without a company-specific UI branch.

### 6. Push still depends on someone initiating refresh — high value

The hosted app has no unattended schedule. The local monitor explicitly refuses remote origins (`scripts/monitor.mjs:1–7`). Jobs advance through browser/API step requests (`lib/services.ts:46–77`), so closing the browser can leave work unfinished. The UI discloses this limitation.

Today also defaults to the saved snapshot. Market watch always uses `snapshotMarkets` (`app/page.tsx:26,50`), including in Today mode; it is correctly labelled as a saved preview, but refreshing will not turn that panel into a view of the new market data. Coverage counts merge saved and current runs while the visible timestamp remains the snapshot timestamp (`app/page.tsx:91`).

**Proposed correction:** authenticated scheduled collection, persistent resumable processing, per-source freshness and failure state, and a current digest driven by current observations. Keep replay as an explicitly selected demo mode. Device notifications are optional; automatic ingestion and a reliable in-app unread queue would already improve the workflow substantially.

**Complete when:** a scheduled run finishes without a browser, creates each eligible alert once, shows its source session/time, and a failed source cannot look like a current successful refresh.

### 7. Inbox prioritisation is shallow and sometimes misclassifies — high value

Only 3 of the 334 saved filings have an exact URL match to an extracted attachment in the saved document library. This is the matching rule currently used by the filing drawer; other aliases may refer to an already indexed document but will not match. Most cards therefore display exchange descriptions plus generic category reasons.

Classification uses the first matching keyword rule (`lib/domain.ts:13–38`). A reproducible “Board Meeting Intimation for Consideration of Buyback of Equity Shares” becomes routine *results* paperwork because the board-meeting rule runs before the capital-action rule. A saved statutory-auditor appointment is classified as management change. Whether an event deserves high priority remains a product judgment, but assigning the wrong underlying event category also defeats category preferences.

**Proposed correction:** model the underlying subject separately from disclosure stage, reconcile related filings, and selectively parse high-value attachments. Add a concise source-backed “what changed / why it matters” for those events. Add official biography enrichment only after the event pipeline is dependable.

**Complete when:** a labelled set of real announcements checks category and priority, buyback/results/call notices remain distinct, and material cards have event-specific evidence rather than only a generic rule explanation.

### 8. Online document collection has avoidable blind spots — high value

The live path downloads at most 12 MB, parses at most 550 pages, has no OCR and does not preserve table structure (`lib/collectors.ts:16–30,63–80`). The earlier DIXON test found four transcripts but rejected its oversized annual report. Larger annual reports in the prepared snapshot used an offline allowance, so prepared and unfamiliar company coverage is uneven.

Discovery takes only the first annual-report link and first four concall rows; it has no alternate provider path when those fail. Requests have timeouts but no backoff or reconciliation of exchange pagination. Twenty-eight snapshot records still carry parser v1 while only five carry v2. Updating the parser alone does not reindex them. Persisting new passages does not remove old passage rows for that document (`lib/services.ts:37–39`).

**Proposed correction:** alternate official-source discovery, controlled large-file/background parsing, selective OCR/table extraction, source retry/backoff, and versioned atomic document replacement. Validate effective source coverage before expanding infrastructure.

**Complete when:** a large annual report and a scanned results page have supported processing paths; failures are resumable; reindexing removes superseded passages; prepared and new companies run through the same documented rules.

### 9. Mobile readability and continuity deserve a dedicated pass — high value

The existing mobile screenshot has a coherent visual style, but the question form and useful answer begin after substantial header, search and coverage content. Important metadata and controls use 7–11 px text in mobile CSS. More concretely, the portfolio volume ratio is hidden on mobile by `.portfolio-row>div:nth-child(4){display:none}` (`app/globals.css:15`). Volume is central to one of FINN's alert workflows.

Navigation and selected company/question exist only in component state; there are no shareable company/research URLs or restoration after reload. A source job is persisted server-side, but the UI does not discover and resume it after a reload. Loading an answer replaces the research content with a spinner rather than retaining readable context.

**Proposed correction:** show the most useful research content earlier, improve legibility and target sizes, expose price and volume together, preserve query/company/tab in URLs, restore jobs, and retain evidence during answer generation. Verify keyboard use, phone-sized viewports, zoom and error/empty states in a fresh browser pass.

**Complete when:** both alert metrics are usable on a phone, a reviewer can return to a company via a link, an interrupted job resumes, and key actions/evidence remain readable without zooming.

### 10. Engineering checks and release handoff need tightening — medium, required before final handoff

- The 22 existing deterministic tests and TypeScript check passed again during this audit.
- Focused lint over 23 application/test/script files found **34 errors and 3 warnings**, primarily explicit `any` and unused variables. These are maintainability findings, not proof of runtime failure.
- Core UI and service code are compressed into long lines with broad types, making future changes harder to review.
- The API smoke test assumes its custom identity header isolates a test user. Hosting middleware controls that header; prior local behavior used the anonymous namespace. Its cleanup is not in `finally`, and it clears read state rather than restoring the prior state (`tests/api-smoke.mjs:3–16`). Run it only against a controlled test database until isolated.
- There is no checked-in CI workflow enforcing these checks or browser regressions.
- D1 lists whole record collections, and answer/job/run retention is unbounded. Current scale is small; pagination and retention should precede significantly larger use, not require an immediate database rewrite.
- Hyde has server-side secrets, caching, bounded repair and request quotas. Cost is limited by call count rather than a measured spend budget; failures can have incomplete token telemetry. Measure quality/cost before adding more models.
- Anonymous visitors use one `demo` namespace. The current private deployment avoids broad anonymous access; any future public audience needs an explicit per-visitor state and abuse-control design.
- The GitHub repo remains unpublished by the user's choice to use the ZIP. Reviewer access to the private app and repository delivery remain release tasks. The AI history is an honestly labelled filtered export captured earlier, so it needs an updated authentic export before submission. The cover note's links must match the eventual delivery.

**Complete when:** critical regression tests, type checks, lint and build pass from a clean install; API tests restore isolated state on failure; intended evaluator access is tested; final source and build history match the deployed version.

These are work packages, not a commitment to finish every possible feature before shipping. Finish and verify each package before selecting the next. Reassess scope after the core trust and analytical improvements.

## Three additions with a clear product purpose

1. **“What changed since the previous call?”** Show a short comparison with both original excerpts, changed guidance and newly mentioned risks. Build on verified dates and speaker-aware evidence. This is the strongest next innovation.
2. **A guidance watchlist.** Let the investor follow an explicit target until its due period, with Pending / Met / Missed / Not comparable states and matching evidence. Reuse the fact pipeline rather than inventing a management credibility score.
3. **A saved question that resurfaces when new evidence arrives.** For example, “Is cash conversion improving?” becomes an update in the inbox after the next results/transcript is indexed. Link the new answer to what changed and charge only when new evidence exists.

A larger model, more charts, voice, trading features and more report sections do not currently resolve the main observed weaknesses. The first change should be the source integrity work in item 1, with the TCS mismatch as the initial regression case.
